## はじめに

GitHub Actions に workflow dependency lockfile が導入された。
`.github/workflows/actions.lock` に、workflow が依存する action とその commit SHA を記録しておく仕組みである。

<LinkCard href="https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles" />

lockfile と聞いてまず気になったのは、lockfile と workflow 定義がずれたときの挙動だ。
例えば pnpm であれば、`pnpm install --frozen-lockfile` は `package.json` と `pnpm-lock.yaml` が一致しない場合はエラーになる。
GitHub Actions の場合、lockfile を正として実行するのか、workflow 定義を正として実行するのか、そもそも実行されないのか。

lockfile を検証する `gh actions-lock --verify` を CI で回せば、ずれた状態の PR はマージできない。
ただ、それはマージをブロックできるというだけで、ずれた状態の workflow が実行されたときに何が起こるのかは分からない。
ドキュメントを読んでもいまいち確信が持てなかったので、実際に検証用のリポジトリを作って試してみた。

## workflow dependency lockfile とは

workflow で `uses: actions/checkout@v4` のように action を指定すると、GitHub Actions は実行時にその tag や branch が指している commit を解決する。
tag や branch は移動できるため、レビューしたときのコードと実際に実行されるコードが一致する保証はない。
action のメンテナのアカウントが乗っ取られて tag が付け替えられると、その action を使っているすべてのリポジトリで悪意のあるコードが実行されてしまう。
実際に 2025 年には `tj-actions/changed-files` の tag が書き換えられ、CI のシークレットが漏洩する事件も起きている。[^1]

[^1]: https://github.com/advisories/GHSA-mrrh-fwg8-r2c3

これまでは `uses:` に commit SHA を直接書く SHA pinning が推奨されていたが、可読性が悪く、action が内部で使っている action(transitive dependency)までは固定できなかった。
workflow dependency lockfile は、これらをまとめて解決するための仕組みである。

lockfile は GitHub CLI の拡張である `gh actions-lock` で生成する。

<LinkCard href="https://github.com/github/gh-actions-lock" />

```sh
gh extension install github/gh-actions-lock
gh actions-lock          # lockfile を生成・更新する
gh actions-lock --verify # lockfile を検証する (書き込みはしない)
```

生成される lockfile は以下のような形式になっている。

```yaml title=".github/workflows/actions.lock"
# This file is machine-generated by `gh actions-lock`.
# Do not edit by hand; run `gh actions-lock` to update.
# Docs: https://gh.io/actions-lockfile
version: 'v0.0.3'
workflows:
  '.github/workflows/probe.yml':
    - 'actions/checkout@v4.2.2'
  '.github/workflows/verify.yml': []
dependencies:
  'actions/checkout@v4.2.2':
    ref: 'v4.2.2'
    commit: 'sha1-11bd71901bbe5b1630ceea73d27597364c9af683'
    owner_id: 44036562
    repo_id: 197814629
```

`workflows` には各 workflow が依存している action が、`dependencies` にはそれぞれの action が解決された commit が記録される。
`owner_id` と `repo_id` は、リポジトリが削除されて同名のリポジトリが作り直された場合などを検知するためのものである。

ドキュメントには、lockfile に載っている(onboard された)workflow について以下のように書かれている。

- workflow が使うすべての action が lockfile に存在しなければならない
- 実行されるのは lockfile に記録された commit である
- その commit は記録された tag や branch の履歴から到達可能でなければならない

ただ、「存在しなければならない」と書かれていても、存在しないとき実行時にどうなるのかまでは書かれていない。

## 検証環境

検証用に以下のリポジトリを用意した。

<LinkCard href="https://github.com/re-taro/playground_github_actions_lockfile" />

検証対象の workflow は以下の通りである。

```yaml title=".github/workflows/probe.yml"
name: probe

on:
  push:
    branches: ['**']
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  probe:
    runs-on: ubuntu-latest
    steps:
      - name: before-action
        run: echo "BEFORE_ACTION_STEP_RAN event=${{ github.event_name }} sha=${{ github.sha }}"
      - uses: actions/checkout@v4.2.2
      - name: after-action
        run: echo "AFTER_ACTION_STEP_RAN"
```

action の前に `run` だけの step を置いているのは、失敗した場合にそれが job の開始時点なのか、action の step に到達した時点なのかを判別するためである。
また、実際にどの commit の action が実行されたのかは、Set up job のログに出力される `Download action repository 'actions/checkout@v4.2.2' (SHA:...)` で確認できる。

これとは別に、`gh actions-lock --verify` を実行する `verify.yml` も用意した。
ただし、`verify.yml` 自体が `actions/checkout` を使うと、lockfile を書き換えたケースで巻き込まれてしまうため、action を使わずに `git fetch` で checkout している。

main ブランチでは `gh actions-lock` で正しい lockfile を生成しておき、そこから 1 commit だけ進めたブランチを各ケースとして用意した。

| ブランチ                            | 変更内容                                                         | `--verify` の結果      |
| ----------------------------------- | ---------------------------------------------------------------- | ---------------------- |
| `case/1a-workflow-ref-changed`      | workflow の `uses:` だけ `v4.2.1` に変更                         | `ref-changed`, `stale` |
| `case/1b-workflow-new-action`       | workflow に `actions/setup-node@v4.4.0` を追加                   | `not-pinned`           |
| `case/2a-lockfile-ref-changed`      | lockfile の ref だけ `v4.2.1` に変更(SHA も `v4.2.1` のもの)     | `ref-changed`, `stale` |
| `case/2b-lockfile-older-commit`     | lockfile の SHA を `v4.2.2` の親 commit に変更                   | `tag-commit-mismatch`  |
| `case/2c-lockfile-unrelated-commit` | lockfile の SHA を `actions/checkout` の履歴にない commit に変更 | `unreachable-pin`      |
| `case/3-lockfile-stale-entry`       | lockfile に使われていないエントリを追加                          | `stale`                |
| `case/4-unonboarded-workflow`       | lockfile に登録されていない workflow を追加                      | `not-pinned`           |

ケース 1 は「workflow を更新したが lockfile を更新し忘れた」状態、ケース 2 は「lockfile だけが更新されている」状態を想定している。
特に 2b と 2c は、lockfile が手で書き換えられた、つまり改ざんされたケースである。

各ブランチを push し、さらに main への PR を作成して、`push` と `pull_request` の両方のイベントで挙動を確認した。
なお、検証には `gh actions-lock` v0.4.1 を使用している。

## 検証結果

結果を先にまとめると以下のようになった。
`push` と `pull_request` のどちらでも結果は同じだった。

| ブランチ                            | probe の結果    | 挙動                                                |
| ----------------------------------- | --------------- | --------------------------------------------------- |
| `main`                              | success         | lockfile の SHA(`11bd719`)で実行                    |
| `case/1a-workflow-ref-changed`      | startup_failure | run 自体が起動しない                                |
| `case/1b-workflow-new-action`       | startup_failure | run 自体が起動しない                                |
| `case/2a-lockfile-ref-changed`      | startup_failure | run 自体が起動しない                                |
| `case/2b-lockfile-older-commit`     | success         | **lockfile に書かれた古い commit(`e3d2460`)で実行** |
| `case/2c-lockfile-unrelated-commit` | failure         | Set up job で失敗                                   |
| `case/3-lockfile-stale-entry`       | success         | 影響なし                                            |
| `case/4-unonboarded-workflow`       | success         | lockfile を使わず tag を解決して実行                |

結論から言うと、GitHub Actions は lockfile を正として実行する。
lockfile に該当するエントリがなかったとしても、workflow 定義から tag を解決し直すようなフォールバックはしない。
この点では `--frozen-lockfile` と同じ思想に基づいていそうだ。

以下、それぞれの挙動について詳しく見ていく。

### lockfile にエントリがない場合

ケース 1a, 1b, 2a は、workflow が参照している `owner/repo@ref` が lockfile に存在しない状態である。
1a と 1b は workflow 側を変更し、2a は lockfile 側を変更しているが、結果はすべて同じだった。

これらのケースでは、job が 1 つも作られることなく run が `startup_failure` で終了した。
YAML の構文エラーなどで workflow ファイル自体が不正な場合と同じ扱いである。

run にはそれぞれ以下のエラーが表示されていた。

```
Invalid lockfile:
The lockfile is missing `actions/checkout@v4.2.1`. Regenerate it by running `gh actions-lock`.
```

```
Invalid lockfile:
The lockfile is missing `actions/setup-node@v4.4.0`. Regenerate it by running `gh actions-lock`.
```

```
Invalid lockfile:
The lockfile is missing `actions/checkout@v4.2.2`. Regenerate it by running `gh actions-lock`.
```

lockfile の検証は workflow の parse の段階で行われているようで、これらのブランチに対して `workflow_dispatch` を実行しようとすると、API 自体が 422 を返して run が作成されなかった。

```
could not create workflow dispatch event: HTTP 422: Invalid Argument - failed to parse workflow: Invalid dependency lockfile ".github/workflows/actions.lock": workflow ".github/workflows/probe.yml" references actions not present in the lockfile: actions/checkout@v4.2.1 Run 'gh actions-lock' to regenerate the lockfile.
```

また `startup_failure` の run には job が存在しないため、REST API や GraphQL API ではこのエラーメッセージを取得できなかった。
`gh run view` でも「This run likely failed because of a workflow file issue.」としか表示されないので、原因を確認するには Web の画面を見る必要がある。

### エントリはあるが commit を取得できない場合

ケース 2c は、lockfile のエントリは存在するが、そこに記録された SHA が `actions/checkout` の履歴に存在しない状態である。
今回は `actions/setup-node` の commit SHA を書き込んだ。

この場合は job までは作成されたが、Set up job で action の解決に失敗した。

```
Using locked action versions from the workflow's lockfile
Getting action download info
##[error]Unable to resolve action `actions/checkout@v4.2.2`, unable to find version `436c65619b12c9e37ff20a4700145cc387898a7d`
```

{/* TODO: 画像 Set up job で失敗している run の画面 */}

`before-action` の step も実行されていないため、どの step も実行される前に失敗していることが分かる。
ドキュメントにある「fork にしか存在しない commit や、tag や branch から到達できない commit は実行時に拒否される」という挙動はこれのことだろう。

### lockfile の SHA が tag の履歴内にある場合

一番注意する必要なのがケース 2b である。
lockfile の SHA を `v4.2.2` の親 commit(`e3d2460`)に書き換えたところ、run は成功した。

```
Using locked action versions from the workflow's lockfile
Getting action download info
Download action repository 'actions/checkout@v4.2.2' (SHA:e3d2460bbb42d7710191569f88069044cfb9d8cf)
```

{/* TODO: 画像 古い SHA で action がダウンロードされている Set up job のログ */}

ログには `actions/checkout@v4.2.2` と表示されているが、実際にダウンロードされているのは lockfile に書かれた古い commit である。
実行時の検証は「commit が ref の履歴から到達可能か」だけなので、tag が指している commit と一致しているかまでは確認されない。

つまり、lockfile だけを書き換えて、同じ tag の過去の脆弱な commit に戻すような改ざんは実行時には検知できない。
`gh actions-lock --verify` は tag が指している commit と lockfile の commit を比較するため、`tag-commit-mismatch` として検知できる。

```
tag v4.2.2 points at 11bd71901bbe; the lockfile locks e3d2460bbb42, an older commit in its history
```

なお、`gh actions-lock` の README にも、branch や `v4` のような可変な ref を履歴内の古い commit に固定し直した場合は検知できない、という制限が書かれている。
`v4.2.2` のような完全な tag であれば `--verify` で検知できるが、`main` などの branch を参照している場合は `--verify` でも検知できない。

### lockfile に使われていないエントリがある場合

ケース 3 は、lockfile に workflow が使っていないエントリが残っている状態である。
これは `--verify` では `stale` としてエラーになるが、実行時には何の影響もなかった。

### lockfile に登録されていない workflow の場合

ケース 4 は、lockfile の `workflows` に載っていない workflow を新しく追加した状態である。
この workflow は lockfile を使わずに、従来通り tag を解決して実行された。

Set up job のログを見ると、lockfile に登録されている workflow では出力される `Using locked action versions from the workflow's lockfile` が出力されていない。

```
Getting action download info
Download action repository 'actions/checkout@v4.2.2' (SHA:11bd71901bbe5b1630ceea73d27597364c9af683)
```

lockfile はあくまで workflow 単位で onboard するものであり、onboard されていない workflow は lockfile の存在を無視して実行される。
新しい workflow を追加したときに `gh actions-lock` を実行し忘れると、その workflow だけ lockfile の保護から外れることになる。

### pull_request ではどの lockfile が使われるのか

`pull_request` イベントでは、PR の head と base の merge commit 上で workflow が実行される。
ケース 2b を `pull_request` で実行したところ、`github.sha` は merge commit を指しており、ダウンロードされた action は PR で書き換えた古い commit だった。

つまり、PR で lockfile を書き換えると、レビューを経る前の PR の CI でもその lockfile が使われる。

## Require lockfile ポリシー

ケース 4 のように、lockfile に登録されていない workflow が実行されてしまう問題に対しては、Require lockfile というポリシーが用意されている。

<LinkCard href="https://docs.github.com/en/actions/how-tos/administer/enforce-workflow-lockfiles" />

このポリシーは、対象の workflow が lockfile に onboard されていない場合に run をブロックするものである。
enterprise や organization だけでなく、リポジトリの Settings → Actions → Policies からも設定できる。

{/* TODO: 画像 Require lockfile ポリシーの設定画面 */}

なお、執筆時点では REST API のドキュメントや OpenAPI の定義には Require lockfile に対応する rule type が載っておらず、API からポリシーを作成しようとしても 422 になった。
Web の画面から作成したポリシーを API で取得すると、以下のように `require_lockfile` という rule type になっていた。

```json
{
	"name": "require lockfile",
	"enforcement": "active",
	"conditions": { "workflow_path": { "include": ["~ALL"], "exclude": [] } },
	"rules": [{ "type": "require_lockfile" }]
}
```

このポリシーを有効にした状態で、各ケースを再度実行した結果が以下である。

| ブランチ                            | ポリシーなし       | ポリシーあり           |
| ----------------------------------- | ------------------ | ---------------------- |
| `main`                              | success            | success                |
| `case/1a`, `1b`, `2a`               | startup_failure    | startup_failure        |
| `case/2b-lockfile-older-commit`     | 古い commit で実行 | **古い commit で実行** |
| `case/2c-lockfile-unrelated-commit` | failure            | failure                |
| `case/3-lockfile-stale-entry`       | success            | success                |
| `case/4-unonboarded-workflow`       | tag を解決して実行 | **startup_failure**    |

挙動が変わったのはケース 4 だけだった。
lockfile に登録されていない workflow は、以下のエラーで `startup_failure` になった。

```
Workflow is not in the repository's lockfile. Run `gh actions-lock` in the repository and commit the result. If this is a reusable workflow, the maintainer of the reusable workflow needs to run `gh actions-lock` in its repository and commit the result. Workflow file: '.github/workflows/probe-unonboarded.yml'.
The following workflows are missing a lockfile:
 - .github/workflows/probe-unonboarded.yml
```

Require lockfile はあくまで「workflow が lockfile に onboard されているか」を確認するだけのポリシーである。
onboard されている workflow と lockfile の不整合はポリシーがなくても実行時に弾かれるし、ケース 2b のような改ざんはポリシーがあっても防げない。

## 運用で気をつけること

今回の検証を踏まえると、lockfile を運用する上では以下が重要になりそうだ。

- `gh actions-lock --verify` を PR の required check にする
  - 実行時にはケース 2b を検知できないため、これが唯一の機械的な防御になる
  - ケース 1 のような更新漏れも、`startup_failure` より先に分かりやすいエラーとして検出できる
  - `.github/workflows/actions.lock` を CODEOWNERS に追加し、lockfile の変更を必ずレビューする
  - `commit` の変更は、実行されるコードが変わることを意味する
  - branch を参照している action は `--verify` でも古い commit への書き換えを検知できない
- Require lockfile ポリシーを有効にする
  - 新しい workflow の onboard 漏れを防げる
- Dependabot を有効にする
  - Dependabot は action のバージョンを更新するときに lockfile も一緒に更新してくれる

また、`--verify` を実行する workflow 自体が action を使っている場合、lockfile が壊れていると verify の workflow ごと `startup_failure` になる可能性がある。
その場合でも PR がマージできなくなることには変わりないが、何が原因で失敗しているのかが分かりにくくなる。
今回の検証のように、verify の workflow は action を使わずに checkout しておくのも 1 つの手だろう。

## おわりに

workflow dependency lockfile と workflow 定義がずれたときの GitHub Actions の挙動を検証した。

GitHub Actions は lockfile を正として実行し、lockfile にエントリがない場合は workflow 定義にフォールバックせず、run 自体が起動しない。
一方で、lockfile に tag の履歴内の古い commit が書かれている場合は、何の警告もなくその commit で実行されてしまう。
lockfile は実行時の保護と、`--verify` やレビューによる保護を組み合わせて初めて機能するものだと感じた。

SHA pinning と比べて workflow の可読性を保ったまま transitive dependency まで固定できるのは非常に嬉しい。
サプライチェーン攻撃が増えている昨今、ぜひ導入を検討してみてほしい。
